03단계 실습

설정에서 라우팅까지

ConfigMap/Secret으로 설정을 주입하고, 하나의 진입점에서 경로별로 서로 다른 서비스로 트래픽을 나누는 Ingress까지 만들어봅니다. SPA 특유의 "런타임 env 주입" 문제와, kind에는 Ingress 컨트롤러가 기본으로 없다는 함정도 함께 다룹니다.

전제 조건: 02단계의 frontend-practice Deployment/Service가 살아있어야 합니다. kubectl get deploy,svc frontend-practice로 먼저 확인하세요.

ConfigMap 만들기

환경별로 달라질 수 있는 값을 이미지 밖으로 분리합니다.

# frontend-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-config
data:
  API_BASE_URL: "http://backend-mock-service/api"

$ kubectl apply -f frontend-configmap.yaml
$ kubectl get configmap frontend-config -o yaml
무슨 일이 일어나나 ConfigMap은 그 자체로는 아무것도 하지 않는 **단순 key-value 저장소**입니다. etcd에 저장될 뿐이고, 아직 어떤 Pod에도 연결되지 않았습니다. 다음 단계에서 이 값을 Pod 안으로 실제로 주입합니다.
2

SPA에 런타임으로 값 주입하기

이번 실습에서 가장 중요한 함정 — ConfigMap을 연결해도 화면엔 반영이 안 되는 이유를 해결합니다.

왜 문제가 되나 Vite는 import.meta.env.VITE_* 값을 빌드 시점에 JS 번들 안에 그대로 박아버립니다. 02단계에서 만든 frontend-practice:v1 이미지는 이미 빌드가 끝난 정적 파일이라, 컨테이너를 실행할 때 환경변수를 아무리 넣어줘도 이미 번들된 JS 코드는 절대 바뀌지 않습니다. 백엔드 서버라면 process.env를 매 요청마다 읽으니 문제없지만, 정적 파일을 서빙하는 SPA는 구조가 다릅니다. 
# inject-env.sh
#!/bin/sh
set -e
cat <<EOF > /usr/share/nginx/html/env.js
window.__ENV__ = {
  API_BASE_URL: "${API_BASE_URL}"
};
EOF

# Dockerfile의 2단계(nginx)에 추가
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY inject-env.sh /docker-entrypoint.d/40-inject-env.sh
RUN chmod +x /docker-entrypoint.d/40-inject-env.sh
EXPOSE 80
무슨 일이 일어나나 — 낯익은 로그였을 겁니다 nginx 공식 이미지는 컨테이너가 시작될 때 /docker-entrypoint.d/ 안의 실행 가능한 스크립트들을 nginx를 띄우기 직전에 순서대로 실행해주는 기능이 내장돼 있습니다. 사실 01단계에서 kubectl logs nginx-test를 처음 봤을 때 이미 이 문구를 보셨습니다: 
/docker-entrypoint.sh: Looking for shell scripts in /docker-entrypoint.d/
그때는 그냥 지나쳤던 그 메커니즘을 지금 직접 활용하는 겁니다. 컨테이너가 켜질 때마다 이 스크립트가 **그 순간의 환경변수 값**으로 env.js 파일을 새로 생성하고, Vite의 index.html(프로젝트 루트, dist 안이 아님)에 미리 이 줄을 추가해두면: 
<script src="/env.js"></script>
번들 JS가 로드되기 전에 window.__ENV__가 먼저 채워집니다. 빌드는 한 번만 하고, **이미지는 그대로 두고 환경마다 다른 ConfigMap만 바꿔 끼우는 식**으로 재사용할 수 있게 됩니다. 
# frontend-deployment.yaml의 containers 아래 추가
      containers:
        - name: frontend
          image: frontend-practice:v2
          imagePullPolicy: IfNotPresent
          envFrom:
            - configMapRef:
                name: frontend-config
          ports:
            - containerPort: 80

$ docker build -t frontend-practice:v2 .
$ kind load docker-image frontend-practice:v2 --name kind
$ kubectl apply -f frontend-deployment.yaml
확인 kubectl exec deploy/frontend-practice -- cat /usr/share/nginx/html/env.js로 실제 값이 채워졌는지 확인해보세요.
3

Secret — "암호화"가 아니라는 것 직접 확인

이름 때문에 생기는 흔한 오해를 실습으로 깹니다.

# frontend-secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: frontend-secret
type: Opaque
stringData:
  API_KEY: "practice-secret-value-1234"

$ kubectl apply -f frontend-secret.yaml
$ kubectl get secret frontend-secret -o yaml
무슨 일이 일어나나 stringData로 넣은 평문이 저장되면서 Base64로 인코딩됩니다. 결과 YAML의 data.API_KEY 필드에 이상한 문자열이 보일 텐데, 이건 암호화된 값이 아니라 그냥 인코딩된 값입니다 — 누구나 즉시 원복할 수 있습니다. 
$ kubectl get secret frontend-secret -o jsonpath='{.data.API_KEY}' | base64 -d
프론트엔드 개발자가 특히 조심할 점 Secret 자체는 etcd 접근 권한이 없는 사람에게는 숨겨지지만, 이걸 2단계에서 만든 env.js 패턴처럼 프론트엔드 컨테이너의 런타임 값으로 주입하면 브라우저가 다운로드해서 실행하는 JS 파일 안에 그대로 노출됩니다. 누구든 "페이지 소스 보기"로 볼 수 있습니다. Secret은 백엔드에서만 쓰는 값(DB 비밀번호, 서버 간 API 키 등)에 쓰는 것이지, 프론트엔드 컨테이너로 흘러들어가는 값을 보호해주는 장치가 아닙니다.
4

가짜 백엔드 만들기 (ConfigMap을 파일로 마운트)

Ingress의 경로 분기를 보여주려면 서로 다른 서비스가 두 개 필요합니다. 이번엔 ConfigMap을 env가 아니라 파일로 붙여봅니다.

# backend-mock.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-mock-html
data:
  index.html: |
    {"message": "hello from backend-mock"}
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-mock
  labels:
    app: backend-mock
spec:
  replicas: 1
  selector:
    matchLabels:
      app: backend-mock
  template:
    metadata:
      labels:
        app: backend-mock
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          volumeMounts:
            - name: html
              mountPath: /usr/share/nginx/html
          ports:
            - containerPort: 80
      volumes:
        - name: html
          configMap:
            name: backend-mock-html
---
apiVersion: v1
kind: Service
metadata:
  name: backend-mock-service
spec:
  selector:
    app: backend-mock
  ports:
    - port: 80

$ kubectl apply -f backend-mock.yaml
무슨 일이 일어나나 — env vs 파일 마운트 2단계에서는 ConfigMap을 envFrom으로 **환경변수**로 붙였다면, 이번엔 volumes.configMap + volumeMounts로 **파일**로 붙였습니다. ConfigMap의 각 key(index.html)가 그대로 마운트 경로 안의 파일 이름이 됩니다. 이미지 안에 아무 파일도 없는 순정 nginx:alpine이지만, 이 마운트 덕분에 우리가 원하는 응답을 반환하는 "가짜 백엔드" 역할을 하게 됩니다.
5

Ingress 컨트롤러 설치

kind에는 Ingress 컨트롤러가 기본으로 없다는 걸 먼저 확인합니다.

$ kubectl get pods -A | grep ingress
# → 아무것도 안 나옴
왜 이 단계가 필요한가 지금까지 만든 Ingress 오브젝트는 사실 "이렇게 라우팅해줘"라는 선언일 뿐, 그 자체로는 트래픽을 처리하지 않습니다. 이 선언을 읽고 실제로 프록시 역할을 해줄 컨트롤러가 클러스터에 따로 떠 있어야 합니다. kind는 이걸 기본 설치해주지 않으므로 직접 설치해야 합니다. 
$ kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
$ kubectl wait --namespace ingress-nginx \
    --for=condition=ready pod \
    --selector=app.kubernetes.io/component=controller \
    --timeout=120s
무슨 일이 일어나나 ingress-nginx라는 새 네임스페이스에 컨트롤러 Deployment/Service가 설치됩니다. 이름이 헷갈릴 수 있는데, 이건 우리가 지금까지 쓴 "정적 파일 서빙용 nginx"와는 **다른 역할**입니다 — 이 nginx는 Ingress 오브젝트를 watch하다가, 규칙이 바뀔 때마다 자기 내부 설정을 자동으로 고쳐 쓰는 **리버스 프록시**입니다. wait 명령은 컨트롤러 Pod가 완전히 준비될 때까지 기다려주는 것 — 설치 직후엔 아직 Running이 아닐 수 있습니다.
6

Ingress 규칙 작성

경로에 따라 서로 다른 Service로 트래픽을 나눕니다.

# frontend-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /api
            pathType: Exact
            backend:
              service:
                name: backend-mock-service
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80

$ kubectl apply -f frontend-ingress.yaml
$ kubectl get ingress frontend-ingress
무슨 일이 일어나나 rules[].http.paths가 경로별 분기표입니다. /api(정확히 일치)로 오는 요청은 backend-mock-service로, 그 외 /로 시작하는 모든 요청(Prefix)은 frontend-service로 갑니다. rewrite-target: / 어노테이션이 중요한데, 이게 없으면 컨트롤러가 /api 경로 그대로 백엔드에 전달해서 (백엔드엔 index.html 파일 하나뿐이라) 404가 납니다. 이 어노테이션이 실제 전달 직전에 경로를 /로 바꿔주기 때문에 백엔드가 정상 응답합니다.
7

접속 테스트

같은 포트, 다른 경로로 서로 다른 서비스에 도달하는 걸 직접 확인합니다.

$ kubectl port-forward -n ingress-nginx service/ingress-nginx-controller 8080:80
# 다른 터미널에서:
$ curl localhost:8080/
$ curl localhost:8080/api
무슨 일이 일어나나 이번엔 frontend-service나 backend-mock-service가 아니라 Ingress 컨트롤러의 Service로 포트포워딩했습니다. 같은 localhost:8080인데:
  • curl localhost:8080/ → Vite 빌드 결과(title: frontend-practice)
  • curl localhost:8080/api → {"message": "hello from backend-mock"}
진입점은 하나인데 경로에 따라 완전히 다른 Pod 그룹으로 갈라지는 것 — 이게 Service 하나만으로는 못 하던 것(Service는 동질적인 Pod 그룹 하나만 가리킴)이고, Ingress가 추가로 해주는 일입니다.
확인 두 응답이 서로 다르게 나오면 성공입니다.

# Ingress 컨트롤러 자체까지 지우고 싶다면(선택):
$ kubectl delete -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
무슨 일이 일어나나 02단계의 frontend-practice Deployment/Service는 그대로 남겨둡니다 — 다음 단계(파이프라인 자동화)에서 계속 쓸 대상입니다. Ingress 컨트롤러는 이후 단계에서 또 쓸 수 있어서 지우지 않고 놔둬도 무방합니다.
curl localhost:8080/api가 404를 반환하면 대부분 rewrite-target 어노테이션이 빠졌거나 pathType이 잘못된 경우입니다. kubectl describe ingress frontend-ingress로 규칙이 제대로 등록됐는지, kubectl logs -n ingress-nginx deploy/ingress-nginx-controller로 실제로 어떤 경로로 라우팅했는지 확인해보세요.
