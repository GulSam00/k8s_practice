Helm 설치 확인

Helm 자체는 클러스터에 뭘 설치하는 게 아니라, 로컬에 까는 CLI 도구입니다.

$ brew install helm
$ helm version
Helm이 뭔데 지금까지 여러 YAML 파일(frontend-deployment.yaml, frontend-configmap.yaml...)을 따로따로 kubectl apply했습니다. Helm은 이 파일들을 **하나의 배포 단위(차트)**로 묶고, values.yaml 하나로 이미지 태그·replica 수 같은 값을 전부 파라미터화합니다. 지난번 얘기했던 비유 그대로 — 설정 가능한 npm 패키지에 가깝습니다. package.json이 Chart.yaml, .env가 values.yaml 포지션입니다.

기존 리소스를 Helm 차트로 변환

02단계에서 만든 Deployment/Service를 템플릿화합니다.

# 04/frontend-chart/Chart.yaml
apiVersion: v2
name: frontend-practice
description: frontend-practice Helm chart
version: 0.1.0
appVersion: "1.0"

# 04/frontend-chart/values.yaml
replicaCount: 2
image:
  repository: ghcr.io/gulsam00/frontend-practice
  tag: v2
  pullPolicy: IfNotPresent
config:
  apiBaseUrl: "http://backend-mock-service/api"

# 04/frontend-chart/templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
  labels:
    app: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
    spec:
      containers:
        - name: frontend
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          env:
            - name: API_BASE_URL
              value: {{ .Values.config.apiBaseUrl | quote }}
          ports:
            - containerPort: 80

# 04/frontend-chart/templates/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-service
spec:
  selector:
    app: {{ .Release.Name }}
  ports:
    - port: 80
      targetPort: 80
무슨 일이 일어나나 {{ .Values.xxx }}는 Go 템플릿 문법입니다. helm install/upgrade 시점에 values.yaml(또는 --set 플래그)의 실제 값으로 치환된 뒤, 그 결과가 평범한 k8s YAML이 되어 API 서버로 전송됩니다. {{ .Release.Name }}는 우리가 helm install할 때 붙이는 릴리스 이름이 자동으로 들어갑니다 — 오브젝트 이름을 하드코딩 안 해도 되는 이유.

Helm으로 배포 전환

기존 kubectl 리소스를 지우고, 같은 걸 Helm 릴리스로 다시 띄웁니다.

$ kubectl delete deploy,svc frontend-practice
$ helm install frontend-practice ./04/frontend-chart
$ helm list
$ kubectl get pods -l app=frontend-practice
무슨 일이 일어나나 helm install은 템플릿을 렌더링해서 만든 YAML을 내부적으로 kubectl apply와 똑같이 API 서버에 보냅니다 — 그 뒤 Deployment 컨트롤러, ReplicaSet 컨트롤러, scheduler, kubelet이 하는 일은 지금까지 배운 것과 **완전히 동일**합니다. 달라진 건 오직 "그 YAML을 누가, 어떻게 만들어서 보냈느냐"뿐입니다. 추가로 Helm은 이 배포를 릴리스(release)라는 단위로 추적해서, helm rollback frontend-practice 1처럼 이전 상태로 되돌리는 것도 지원합니다 (Deployment 자체의 리비전 히스토리와는 별개로, Helm 레벨의 히스토리입니다).

GitHub Actions 워크플로 작성

push할 때마다 이미지를 자동으로 빌드해서 ghcr.io로 올리는 파이프라인을 만듭니다.

# .github/workflows/build.yml (저장소 루트 기준 경로 고정)
name: build-and-push
on:
  push:
    branches: [main]
    paths:
      - '02/frontend-practice/**'

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v5
        with:
          context: ./02/frontend-practice
          push: true
          tags: ghcr.io/gulsam00/frontend-practice:${{ github.sha }}
여기서 자주 터지는 함정 이미지 이름이 ghcr.io/gulsam00/...로 **전부 소문자**인 걸 확인하세요. Docker 레지스트리 규격상 이미지 이름은 반드시 소문자여야 하는데, 저장소 계정이 GulSam00처럼 대문자가 섞여 있으면 ${{ github.repository_owner }}를 그대로 쓰다가 빌드 단계에서 "invalid reference format" 에러가 납니다. 그래서 여기선 직접 소문자로 하드코딩했습니다.
무슨 일이 일어나나 secrets.GITHUB_TOKEN은 우리가 따로 만들 필요 없이 **Actions가 실행될 때마다 자동으로 발급**되는 임시 토큰입니다. permissions.packages: write를 선언해줘야 이 토큰으로 ghcr.io에 푸시할 권한이 생깁니다. paths 필터 덕분에 02/frontend-practice/ 밖의 파일(예: 이 아티팩트용 설명 파일)만 바뀌면 워크플로가 아예 실행되지 않습니다.

푸시해서 파이프라인 실행

실제로 커밋을 올려서 파이프라인이 도는 걸 확인합니다.

$ git add .github/workflows/build.yml 04/
$ git commit -m "add helm chart and ci pipeline"
$ git push origin main
$ gh run watch
무슨 일이 일어나나 git push가 GitHub에 새 커밋을 전달하는 순간, GitHub 서버가 .github/workflows/build.yml의 on.push 조건과 매치되는 걸 확인하고 **GitHub이 관리하는 임시 우분투 가상머신**을 하나 띄워 워크플로를 실행합니다. 이 가상머신 안에서 우리 저장소를 체크아웃하고, 02단계에서 우리가 손으로 했던 docker build + 레지스트리 로그인 + 푸시를 그대로 자동 수행합니다. gh run watch(GitHub CLI)로 실시간 로그를 터미널에서 볼 수 있습니다. 없으면 저장소의 Actions 탭에서 확인하세요.
확인 저장소의 Packages 탭(또는 https://github.com/GulSam00?tab=packages)에 frontend-practice 패키지가 새로 생겼는지 확인하세요.

패키지 공개 설정

kind 클러스터가 별도 인증 없이 이미지를 받아올 수 있게 합니다.

왜 필요한가 GITHUB_TOKEN으로 올린 패키지는 기본적으로 **비공개**입니다. 우리 kind 클러스터엔 ghcr.io 인증 정보가 없어서, 이 상태로는 ImagePullBackOff가 납니다(02단계 때와 원인은 다르지만 증상은 같습니다 — 이번엔 "로컬에 이미지가 없어서"가 아니라 "인증이 없어서"). 학습용으로 가장 간단한 해결은 패키지를 공개로 바꾸는 것입니다.
해결 방법 GitHub 저장소 → Packages 탭 → frontend-practice 클릭 → Package settings → Change visibility → Public. (실무의 사설 레지스트리라면 대신 kubectl create secret docker-registry로 imagePullSecrets를 만들어 Deployment에 연결하는 방식을 씁니다 — 지금은 학습 목적상 더 간단한 공개 전환으로 갑니다.)

새 이미지로 Helm 업그레이드

이번엔 kind load 없이, 진짜 레지스트리에서 이미지를 받아옵니다.

$ git log -1 --format=%H
# 위에서 나온 커밋 해시를 태그로 사용
$ helm upgrade frontend-practice ./04/frontend-chart \
    --set image.tag=<커밋-해시>
$ kubectl get pods -l app=frontend-practice -o wide
$ kubectl describe pod <새-pod-이름> | grep -A3 Events
무슨 일이 일어나나 — 02단계와 정반대 상황 02단계에서는 kind load docker-image로 로컬 이미지를 강제로 노드에 밀어넣어야 했습니다. 이번엔 이미지가 **실제 ghcr.io 레지스트리**에 있으므로, kubelet이 Pulling image "ghcr.io/gulsam00/frontend-practice:..."를 시도해서 **인터넷을 통해 정식으로 pull**해옵니다. describe pod의 Events에 Pulling/Pulled가 찍히는 걸 보면, 이번엔 로컬 캐시가 아니라 진짜 원격에서 받아왔다는 게 확인됩니다.

ArgoCD 설치

"Git 저장소 상태 = 클러스터가 유지해야 할 상태"를 대신 감시해줄 컨트롤러를 설치합니다.

$ kubectl create namespace argocd
$ kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
$ kubectl wait --namespace argocd \
    --for=condition=available deployment/argocd-server \
    --timeout=180s
무슨 일이 일어나나 지금까지는 우리가 직접 helm upgrade를 실행해야 클러스터가 바뀌었습니다. ArgoCD는 그 역할을 **컨트롤러**가 대신하게 만듭니다 — 01단계에서 배운 "지켜보다가 차이나면 스스로 반응하는" 패턴을, "Pod 개수"가 아니라 "**Git 저장소의 내용**"을 대상으로 적용하는 겁니다. 설치되는 구성요소도 지난번 ingress-nginx와 비슷한 패턴입니다: 여러 컨트롤러 Pod, RBAC, 그리고 자체 UI/API 서버.

Application 등록 — GitOps 관찰하기

Git 저장소를 가리키는 Application을 만들고, 자동 동기화를 직접 눈으로 봅니다.

# frontend-argo-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-practice
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/GulSam00/k8s_practice.git
    targetRevision: main
    path: 04/frontend-chart
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      selfHeal: true
      prune: true

$ kubectl apply -f frontend-argo-app.yaml
$ kubectl get application -n argocd
무슨 일이 일어나나 Application도 그냥 또 하나의 커스텀 리소스(CRD)입니다 — 예전에 배운 것처럼, ArgoCD가 설치되면서 kind: Application이라는 새 타입을 클러스터에 등록해둔 겁니다. ArgoCD 컨트롤러가 이 오브젝트를 watch하다가, repoURL의 04/frontend-chart 경로(우리가 2단계에서 만든 Helm 차트)를 주기적으로 확인합니다. selfHeal: true이면, 누군가 kubectl로 클러스터를 직접 고쳐도(Git과 어긋나면) ArgoCD가 **Git 상태로 되돌립니다** — 09단계에서 겪었던 "Pod를 지워도 ReplicaSet이 되살리는" 것과 똑같은 원리가, 이번엔 "누가 클러스터를 손으로 고쳐도 Git 상태로 되돌린다"는 훨씬 큰 스케일로 적용된 겁니다.
확인 kubectl port-forward svc/argocd-server -n argocd 8081:443 후 https://localhost:8081 접속(초기 admin 비밀번호는 kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d)해서 UI로도 동기화 상태를 확인해보세요.

정리

이번 단계에서 만든 것들을 정리합니다.

$ kubectl delete -f frontend-argo-app.yaml
$ kubectl delete namespace argocd
$ helm uninstall frontend-practice
무슨 일이 일어나나 helm uninstall은 이 릴리스가 만들었던 오브젝트를 전부 역순으로 지웁니다 (Helm이 릴리스 단위로 "내가 뭘 만들었는지" 추적하고 있기 때문에 가능한 일). GitHub Actions 워크플로와 ghcr.io 이미지는 저장소/계정에 남아있어도 무방합니다 — 다음에 다시 helm install하면 그대로 재사용됩니다.
ImagePullBackOff가 나면 6단계(패키지 공개 설정)를 확인하시고, invalid reference format이 뜨면 4단계의 소문자 이미지 이름 함정을 다시 보세요. ArgoCD Application이 계속 OutOfSync면 kubectl describe application frontend-practice -n argocd의 마지막 이벤트를 확인하세요.
