02단계 실습

빌드에서 배포까지

간단한 Vite + React 앱을 실제로 빌드하고, Docker 이미지로 만들고, kind 클러스터 안에 배포해서 브라우저로 접속하기까지의 전 과정입니다. 특히 "로컬에서 빌드한 이미지가 왜 클러스터에서 안 보이는지" 같은, 실전에서 누구나 한 번은 겪는 함정을 짚고 넘어갑니다.

전제 조건: 01단계에서 만든 kind-kind 클러스터(control-plane 1 + worker 2)가 살아있어야 합니다. kubectl get nodes로 먼저 확인하세요.

예제 앱 만들기

배포 대상이 될 최소한의 React 앱을 스캐폴딩합니다.

$ npm create vite@latest frontend-practice -- --template react
$ cd frontend-practice
$ npm install
무슨 일이 일어나나 평소 하던 그대로입니다 — 로컬 개발 환경을 만드는 단계라 k8s와는 아직 무관합니다. npm/yarn/pnpm 뭘 쓰셔도 무방하며, 이후 명령어의 npm만 대응되게 바꾸면 됩니다.
2

프로덕션 빌드로 배포물 확인

우리가 실제로 배포할 대상은 소스코드가 아니라 이 빌드 결과물입니다.

$ npm run build
$ ls dist
무슨 일이 일어나나 dist/에 해시가 붙은 정적 HTML/CSS/JS 파일들이 생깁니다. 이 폴더 안의 파일들이 앞으로 만들 컨테이너 이미지의 실체입니다 — k8s는 React나 Vite를 전혀 모릅니다. k8s 입장에서는 그냥 "정적 파일을 서빙하는 컨테이너 하나"일 뿐입니다.
3

Dockerfile 작성 (멀티스테이지)

빌드 환경과 서빙 환경을 분리해서, 최종 이미지에 node_modules가 남지 않게 합니다.

# Dockerfile
# --- 1단계: 빌드 전용, 이 레이어는 최종 이미지에 남지 않음 ---
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# --- 2단계: 실제로 배포되는 이미지 ---
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
무슨 일이 일어나나 FROM이 두 번 나오는 게 핵심입니다.
  1. 1단계(build): node 이미지 안에서 npm ci + npm run build를 실행 — 이 단계의 파일시스템(node_modules 포함)은 통째로 임시로만 존재합니다.
  2. 2단계(nginx): COPY --from=build로 1단계의 /app/dist 폴더만 쏙 뽑아와서 nginx 이미지 위에 얹습니다. node, npm, node_modules는 전부 버려집니다.
결과적으로 최종 이미지는 nginx + 정적 파일뿐이라 용량이 훨씬 작고, 빌드 도구가 배포 환경에 남아있지 않아 더 안전합니다.
4

이미지 빌드

Dockerfile을 실제 이미지로 만듭니다.

$ docker build -t frontend-practice:v1 .
$ docker images | grep frontend-practice
무슨 일이 일어나나 Docker 데몬이 Dockerfile을 한 줄씩 실행해서 이미지를 만들고, 맥 호스트의 Docker 이미지 저장소에 `frontend-practice:v1`이라는 이름(태그)으로 저장합니다. 아직 kind 클러스터와는 아무 관련이 없습니다 — 다음 단계에서 이게 왜 문제가 되는지 나옵니다.
5

이미지를 kind 클러스터로 전달

이번 실습에서 가장 중요한 함정 — 방금 만든 이미지는 클러스터에서 아직 보이지 않습니다.

$ kind load docker-image frontend-practice:v1 --name kind
왜 이 단계가 필요한가 지난번에 확인했듯 kind의 노드는 각각 독립된 Docker 컨테이너이고, 그 안에서 containerd가 자기만의 별도 이미지 저장소를 갖고 있습니다. 방금 docker build로 만든 이미지는 맥 호스트의 Docker 저장소에만 있지, kind-worker 컨테이너 내부의 containerd는 그 이미지의 존재 자체를 모릅니다. 그래서 이 단계 없이 바로 배포하면 ErrImageNeverPull 또는 ImagePullBackOff 에러가 납니다 — 레지스트리에서 받아오려고 시도하다 실패하는 것도 아니고, 애초에 로컬에서도 못 찾는 것뿐입니다.
무슨 일이 일어나나 kind load docker-image는 내부적으로 이미지를 docker save로 tar 스트림을 뽑아서, 각 노드 컨테이너 안으로 흘려보낸 뒤 그 노드의 containerd가 import하게 만듭니다. 레지스트리 없이 로컬 클러스터에 이미지를 직접 꽂아 넣는 kind만의 방법입니다.
확인 docker exec kind-worker crictl images | grep frontend-practice — 노드 내부 containerd의 이미지 목록에 잡히는지 직접 확인해보세요.

Deployment로 배포

01단계와 같은 패턴, 이미지만 우리가 만든 것으로 바꿉니다.

# frontend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-practice
  labels:
    app: frontend-practice
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend-practice
  template:
    metadata:
      labels:
        app: frontend-practice
    spec:
      containers:
        - name: frontend
          image: frontend-practice:v1
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 80

$ kubectl apply -f frontend-deployment.yaml
$ kubectl get pods -l app=frontend-practice
무슨 일이 일어나나 imagePullPolicy: IfNotPresent를 명시한 게 포인트입니다. 기본값은 태그가 :latest면 Always(매번 레지스트리 확인), 그 외 태그(우리처럼 :v1)면 원래 IfNotPresent라 사실 안 적어도 동작하지만, 명시적으로 적어두면 "이건 로컬에만 있는 이미지라 레지스트리에서 새로 받아오면 안 된다"는 의도가 코드에 그대로 드러납니다. 이걸 안 지키고 실수로 :latest를 쓰면, k8s가 매번 원격 레지스트리에서 같은 이름의 이미지를 찾으려다 실패합니다.
7

Service로 안정적인 주소 만들기

방금 배운 Service 개념을 실제로 적용합니다.

# frontend-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
spec:
  selector:
    app: frontend-practice
  ports:
    - port: 80
      targetPort: 80

$ kubectl apply -f frontend-service.yaml
$ kubectl get endpoints frontend-service
무슨 일이 일어나나 spec.selector가 Deployment의 Pod 라벨과 같은 app: frontend-practice를 가리킵니다. Service가 만들어지는 즉시, 그 라벨을 가진 현재 Pod 2개의 IP가 자동으로 Endpoints 오브젝트에 채워집니다. get endpoints로 그 IP 목록이 실제로 채워졌는지 바로 확인할 수 있습니다 — 이게 Service가 "지금 살아있는 Pod들"을 실시간으로 추적하고 있다는 증거입니다.
8

브라우저로 접속 확인

이번엔 Pod가 아니라 Service를 통해 접속합니다.

$ kubectl port-forward service/frontend-service 8080:80
# 다른 터미널/브라우저에서:
$ curl localhost:8080
무슨 일이 일어나나 01단계에서는 pod/nginx-test로 특정 Pod 하나에 직접 터널을 뚫었지만, 이번엔 service/frontend-service로 뚫었습니다. Service를 통하면 그 뒤에 Pod가 몇 개든(지금은 2개), Pod가 재배치되든 상관없이 같은 주소로 항상 접속됩니다. Vite 앱의 기본 화면이 그대로 브라우저에 뜨면 성공입니다.
9

정리

클러스터를 깨끗하게 되돌립니다.

$ kubectl delete -f frontend-service.yaml -f frontend-deployment.yaml
무슨 일이 일어나나 한 파일이 아니라 -f를 두 번 써서 여러 매니페스트를 한 번에 지울 수 있습니다. Deployment가 지워지면 지난번처럼 ReplicaSet과 Pod까지 연쇄적으로 정리되고, Service는 별도 오브젝트라 따로 지정해줘야 같이 사라집니다.
확인 kubectl get all -l app=frontend-practice 결과가 비어있으면 02단계 완료입니다.
ImagePullBackOff나 ErrImageNeverPull이 뜨면 십중팔구 5단계(kind load docker-image)를 빼먹은 경우입니다. kubectl describe pod <이름>의 Events에서 정확한 에러 메시지를 확인해보세요.
