05단계 실습

죽여보고 배우기

probe를 일부러 잘못 설정해서 멀쩡한 앱을 재시작 지옥에 빠뜨려보고, 메모리 제한을 너무 낮게 잡아서 실제로 OOMKilled를 발생시켜본 다음, 부하를 줘서 HPA가 스스로 Pod를 늘리는 것까지 직접 눈으로 봅니다. 읽어서 아는 것과, 원인 메시지를 직접 마주하고 고쳐본 것의 차이를 만드는 게 목표입니다.

04단계에서 클러스터를 비웠으므로, 1단계에서 앱을 다시 배포합니다. 이미지는 ghcr.io/gulsam00/frontend-practice (04단계에서 검증된 public 이미지)를 그대로 씁니다.

앱 다시 배포

이번 단계는 Helm/ArgoCD 없이 순수 kubectl로 진행합니다 — probe/resource 개념에만 집중하기 위해서입니다.

# 05/frontend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-practice
  labels:
    app: frontend-practice
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend-practice
  template:
    metadata:
      labels:
        app: frontend-practice
    spec:
      containers:
        - name: frontend
          image: ghcr.io/gulsam00/frontend-practice:ca843471503d2e77f2ca91ea4295dba185714424
          ports:
            - containerPort: 80

# 05/frontend-service.yaml — 02단계와 동일
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
spec:
  selector:
    app: frontend-practice
  ports:
    - port: 80

$ kubectl apply -f 05/frontend-deployment.yaml -f 05/frontend-service.yaml
$ kubectl get pods -l app=frontend-practice
무슨 일이 일어나나 이 이미지는 04단계에서 이미 ghcr.io에 올라가 있고 패키지도 public으로 바꿔둔 상태라, kind load 없이도 바로 pull됩니다. probe나 resource 필드는 아직 하나도 없는 "제일 기본적인" Deployment로 시작해서, 이후 단계마다 하나씩 추가해나갑니다.

Liveness / Readiness probe 추가

"살아있다"와 "요청 받을 준비가 됐다"가 서로 다른 질문이라는 걸 코드로 표현합니다.

# frontend-deployment.yaml의 containers 아래 추가
      containers:
        - name: frontend
          image: ghcr.io/gulsam00/frontend-practice:ca843471503d2e77f2ca91ea4295dba185714424
          ports:
            - containerPort: 80
          livenessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 3
            periodSeconds: 5
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 1
            periodSeconds: 3

$ kubectl apply -f 05/frontend-deployment.yaml
두 probe의 질문이 다릅니다
  • livenessProbe: "이 컨테이너가 죽었나?" — 계속 실패하면 kubelet이 컨테이너를 강제로 재시작시킵니다. 응답 없는 좀비 프로세스를 되살리는 용도.
  • readinessProbe: "이 Pod가 지금 트래픽을 받아도 되나?" — 실패해도 Pod를 죽이지 않고, 대신 Service의 Endpoints 목록에서 잠깐 빼버립니다. 시작 중이거나 일시적으로 느려진 Pod로 트래픽이 안 가게 막는 용도.
nginx는 뜨자마자 바로 200을 반환하니 지금은 둘 다 거의 즉시 통과합니다.
확인 kubectl describe pod <이름>에서 Liveness/Readiness 줄이 보이는지 확인하세요.
3

일부러 망가뜨려보기 — probe 오작동

"probe 설정이 잘못되면 멀쩡한 앱도 계속 재시작된다"를 직접 겪습니다.

# livenessProbe의 path를 존재하지 않는 경로로 변경
          livenessProbe:
            httpGet:
              path: /this-path-does-not-exist
              port: 80
            initialDelaySeconds: 3
            periodSeconds: 5
            failureThreshold: 1

$ kubectl apply -f 05/frontend-deployment.yaml
$ kubectl get pods -l app=frontend-practice -w
무슨 일이 일어나나 앱 코드는 전혀 안 바꿨는데(진짜 nginx는 여전히 정상 동작 중), 존재하지 않는 경로를 확인하는 probe가 계속 404를 받고 "죽었다"고 오판합니다. failureThreshold: 1이라 한 번만 실패해도 바로 재시작 — RESTARTS 카운트가 계속 올라가는 걸 보게 될 겁니다. 실제로 5xx를 내는 진짜 장애와, 이런 **probe 오설정으로 인한 가짜 장애**를 구분하는 게 운영에서 중요한 이유입니다. 
$ kubectl describe pod <재시작 중인 pod> | grep -A5 Events
확인 후 원복 Events에 Liveness probe failed: HTTP probe failed with statuscode: 404가 반복되는 걸 확인했으면, path를 다시 /로 되돌리고 failureThreshold도 기본값(3)으로 돌려서 재적용하세요.
4

Resource requests/limits 추가

이 컨테이너가 얼마나 쓸 거라고 선언하는지, 그리고 그 선언이 두 가지 다른 일을 한다는 걸 봅니다.

# containers 아래 추가
          resources:
            requests:
              cpu: "50m"
              memory: "32Mi"
            limits:
              cpu: "100m"
              memory: "64Mi"
requests와 limits는 쓰이는 곳이 다릅니다
  • requests: scheduler가 노드를 고를 때 "이 노드에 이만큼 여유가 있나?"를 판단하는 기준(01단계에서 배운 scheduler의 배치 알고리즘이 실제로 보는 숫자입니다). Pod가 뜬 뒤에는 강제하지 않습니다.
  • limits: 실제로 이 이상 못 쓰게 커널이 강제하는 상한. CPU는 초과하면 그냥 느려지고(throttling), 메모리는 초과하면 프로세스가 강제 종료됩니다 — 다음 단계에서 직접 봅니다.
5

OOMKilled 직접 발생시키기

메모리 limit을 실제 필요량보다 낮게 잡아서, 컨테이너가 강제 종료되는 걸 직접 봅니다.

# limits.memory를 nginx가 뜨기에도 부족한 수준으로
          resources:
            requests:
              cpu: "50m"
              memory: "8Mi"
            limits:
              cpu: "100m"
              memory: "8Mi"

$ kubectl apply -f 05/frontend-deployment.yaml
$ kubectl get pods -l app=frontend-practice -w
무슨 일이 일어나나 nginx가 여러 워커 프로세스를 띄우는 데 8Mi로는 부족합니다. 커널의 cgroup 메모리 제한에 걸리는 순간, 리눅스가 그 컨테이너의 프로세스를 강제로 죽입니다(OOM Killer). kubectl get pods의 STATUS가 OOMKilled로 뜨는 걸 볼 수 있을 겁니다. 이건 probe가 죽인 게 아니라, **커널이 직접 개입**한 겁니다. 
$ kubectl describe pod <pod 이름> | grep -A5 "Last State"
확인 포인트 Last State: Terminated, Reason: OOMKilled, Exit Code: 137이 보일 겁니다. 종료 코드 137은 128+9로, 리눅스 시그널 9(SIGKILL)를 받고 즉사했다는 뜻입니다 — probe 실패로 인한 정상 종료(graceful)와 달리, 준비할 시간도 없이 강제 종료됐다는 신호입니다. 확인 후 memory 값을 4단계의 32Mi/64Mi로 되돌리세요.
6

metrics-server 설치

kind에는 이것도 기본으로 없습니다 — HPA와 kubectl top이 이걸 필요로 합니다.

$ kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
$ kubectl patch deployment metrics-server -n kube-system --type='json' \
    -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
$ kubectl wait --namespace kube-system \
    --for=condition=available deployment/metrics-server --timeout=120s
$ kubectl top pods
왜 patch가 필요한가 metrics-server는 기본적으로 각 노드 kubelet의 인증서를 엄격하게 검증합니다. kind 노드는 로컬 개발용 자체 서명 인증서를 쓰는데, 이게 metrics-server 기본 설정의 신뢰 체인과 안 맞아서 x509: certificate signed by unknown authority 에러가 납니다. --kubelet-insecure-tls는 "로컬 개발 클러스터니까 그 검증은 건너뛰어라"는 kind 환경 전용 우회 설정입니다 (실제 프로덕션 클러스터에서는 보통 필요 없습니다).
확인 kubectl top pods에서 각 Pod의 실제 CPU/메모리 사용량 숫자가 나오면 성공입니다.
7

HPA(자동 스케일러) 만들기

10단계에서 손으로 했던 kubectl scale을, 이번엔 CPU 사용률을 보고 자동으로 하게 만듭니다.

# 05/frontend-hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: frontend-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend-practice
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50

$ kubectl apply -f 05/frontend-hpa.yaml
$ kubectl get hpa frontend-hpa
무슨 일이 일어나나 HPA도 01단계에서 배운 것과 같은 컨트롤 루프입니다 — 다만 감시 대상이 "Pod 개수"가 아니라 "CPU 사용률"입니다. scaleTargetRef로 어떤 Deployment를 조절할지 지정하고, metrics-server가 수집한 실제 CPU 사용량이 4단계에서 정한 requests.cpu(50m)의 50%를 넘으면, HPA 컨트롤러가 replicas 필드를 직접 늘립니다 — 그러면 그 뒤는 항상 봐왔던 ReplicaSet 컨트롤러가 처리합니다.

부하를 줘서 스케일 아웃 관찰

HPA가 실제로 반응하는 걸 실시간으로 지켜봅니다.

# 터미널 A: 부하 생성용 임시 Pod
$ kubectl run load-generator --image=busybox --restart=Never -- \
    /bin/sh -c "while true; do wget -q -O- http://frontend-service > /dev/null; done"

# 터미널 B: 지켜보기
$ kubectl get hpa frontend-hpa -w
# 터미널 C: 지켜보기
$ kubectl get pods -l app=frontend-practice -w
무슨 일이 일어나나 busybox 하나가 frontend-service에 무한 반복으로 요청을 쏘면서 CPU 사용량을 끌어올립니다. HPA는 기본적으로 15초 간격으로 metrics-server 수치를 확인하는데, TARGETS 컬럼(현재 사용률/목표 사용률)이 50%를 넘어가면 REPLICAS가 2에서 서서히 늘어나는 걸 보게 될 겁니다. 늘어난 만큼 부하가 여러 Pod에 분산되면서 다시 평형점을 찾습니다.
확인 다 보셨으면 kubectl delete pod load-generator로 부하 생성기부터 지우세요 — 그래야 그다음 replicas가 서서히 다시 줄어드는(스케일 인) 것도 관찰할 수 있습니다.

정리

이번 단계에서 만든 것들을 정리합니다.

$ kubectl delete pod load-generator --ignore-not-found
$ kubectl delete -f 05/frontend-hpa.yaml
$ kubectl delete -f 05/frontend-deployment.yaml -f 05/frontend-service.yaml
# metrics-server는 다음 단계에서도 유용하니 남겨둬도 무방
HPA가 15~20초가 지나도 안 움직이면 kubectl describe hpa frontend-hpa의 Events를 먼저 보세요 — unable to get metrics가 찍혀있다면 6단계의 metrics-server 설치나 patch가 제대로 안 됐을 가능성이 큽니다. kubectl top pods가 먼저 정상 동작하는지로 원인을 좁힐 수 있습니다.
