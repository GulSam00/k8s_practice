01단계 실습

Pod에서 Deployment까지

클러스터를 다시 띄우고, bare Pod를 직접 만들어보고 지워서 사라지는 걸 본 다음, 같은 걸 Deployment로 만들어서 "왜 사라지지 않는지"를 직접 눈으로 확인하는 12단계 실습입니다. 각 명령어 아래에 실행하는 순간 클러스터 내부에서 벌어지는 일을 정리했습니다.

클러스터가 삭제된 상태입니다 — 이번 실습 0단계에서 기존과 같은 구성(control-plane 1 + worker 2)으로 다시 만듭니다.

1

클러스터 새로 만들기

지난 실습에서 쓰던 것과 같은 구성(control-plane 1대 + worker 2대)으로 kind 클러스터를 다시 띄웁니다.

# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker

$ kind create cluster --config kind-config.yaml
$ kubectl config current-context
무슨 일이 일어나나 kind는 실제 VM 대신 Docker 컨테이너를 노드처럼 사용합니다. 이 한 줄이 하는 일:
  1. Docker 데몬에게 컨테이너 3개 생성을 요청 (config의 노드 3개 = 컨테이너 3개)
  2. 각 컨테이너 안에 containerd(컨테이너 런타임)를 미리 설치해서 띄움 — 이 컨테이너들이 "노드"로 동작
  3. control-plane 역할 컨테이너에 kubeadm으로 API 서버·etcd·scheduler·controller-manager를 부트스트랩
  4. 나머지 worker 컨테이너들이 control-plane에 kubeadm join으로 합류
  5. 클러스터 접속 정보를 ~/.kube/config에 kind-kind 컨텍스트로 써넣고 현재 컨텍스트로 전환
지난번에 확인했듯 이 컨테이너들을 띄우려면 Docker 데몬이 반드시 떠 있어야 합니다.
확인 명령이 끝나면 current-context가 kind-kind여야 합니다. docker ps로 kind-control-plane, kind-worker, kind-worker2 컨테이너 3개가 떠 있는지도 확인해보세요.
2

클러스터가 살아있는지 확인

명령어를 실행하기 전에, kubectl이 어디에 말을 거는지부터 확인합니다.

$ kubectl cluster-info
$ kubectl get nodes -o wide
무슨 일이 일어나나 kubectl은 그 자체로는 아무 로직도 없는 얇은 클라이언트입니다. ~/.kube/config에서 현재 컨텍스트(여기선 kind-kind)의 API 서버 주소와 인증서를 읽어 HTTPS로 API 서버에 요청을 보낼 뿐입니다.
  1. cluster-info는 API 서버에 "살아있냐"고 물어보는 가장 기본적인 헬스체크입니다.
  2. get nodes는 API 서버가 etcd에 저장된 Node 오브젝트 목록을 그대로 돌려주는 것입니다. 각 노드의 kubelet이 주기적으로(기본 10초) "나 살아있다"는 하트비트를 보내고, 그게 끊기면 노드 상태가 NotReady로 바뀝니다.
확인 노드 3개 모두 STATUS가 Ready여야 합니다.
3

bare Pod 하나 직접 만들기

가장 원초적인 방법(imperative)으로 Pod 하나를 띄워, 클러스터 내부 파이프라인을 관찰합니다.

$ kubectl run nginx-test --image=nginx:alpine --port=80
무슨 일이 일어나나 이 한 줄이 실행되는 동안 6단계가 순차적으로 일어납니다.
  1. kubectl이 Pod 스펙(JSON)을 만들어 API 서버에 POST
  2. API 서버가 인증/인가를 확인하고 etcd에 저장 — 이 시점엔 nodeName이 비어있음 (아직 어느 노드에 둘지 안 정해짐)
  3. scheduler가 "노드 미배정 Pod" 목록을 watch하다가 이 Pod를 발견
  4. scheduler가 조건(자원 여유 등)에 맞는 노드를 골라 nodeName을 채워 넣음 (binding)
  5. 그 노드의 kubelet이 "내 노드에 새 Pod가 배정됐다"를 감지 → containerd에 이미지 pull + 컨테이너 생성 요청
  6. kubelet이 컨테이너 상태(Running)를 다시 API 서버에 보고 → etcd 업데이트
scheduler, kubelet 모두 "명령을 받는 것"이 아니라 API 서버를 지켜보다가(watch) 스스로 반응하는 구조라는 점이 핵심입니다.
4

방금 일어난 일을 타임라인으로 보기

2단계에서 설명한 6단계가 실제로 기록돼 있는지 확인합니다.

$ kubectl get pods -o wide
$ kubectl describe pod nginx-test
무슨 일이 일어나나 describe는 새로운 정보를 만들지 않고, etcd에 쌓여있는 이 Pod의 상태 + 최근 Events를 정리해서 보여줄 뿐입니다. 맨 아래 Events 섹션을 보면 Scheduled → Pulling → Pulled → Created → Started 순서가 타임스탬프와 함께 그대로 찍혀 있습니다 — 방금 이론으로 설명한 과정의 실제 로그입니다.
확인 Events 맨 아래 줄이 Started이고, 위 STATUS가 Running인지.
5

로그 확인 + 포트포워딩으로 접속

Service 없이도 개별 Pod에 직접 접속할 수 있다는 걸 확인합니다.

$ kubectl logs nginx-test
$ kubectl port-forward pod/nginx-test 8080:80
# 다른 터미널에서:
$ curl localhost:8080
무슨 일이 일어나나 logs는 컨테이너 런타임이 그 노드에 저장해둔 stdout/stderr를 kubelet이 API 서버를 통해 중계해서 보여주는 것입니다. port-forward는 훨씬 재미있는데, 내 로컬 8080 포트 → API 서버 → 해당 노드의 kubelet → 컨테이너의 네트워크 네임스페이스까지 터널을 뚫습니다. Service나 Ingress 없이도 디버깅용으로 개별 Pod에 바로 접속할 수 있는 이유입니다.
6

컨테이너 내부로 들어가기

nginx가 서빙 중인 정적 파일 위치를 직접 눈으로 봅니다.

$ kubectl exec -it nginx-test -- sh
# 컨테이너 안에서:
/# ls /usr/share/nginx/html
/# exit
무슨 일이 일어나나 exec도 port-forward처럼 API 서버 → kubelet을 거치는 스트림이지만, 이번엔 셸을 그 컨테이너의 프로세스 네임스페이스 안에서 실행시켜 붙여줍니다. 로컬 SSH 접속과 비슷하지만, 실제로는 "이미 떠 있는 프로세스 옆에 새 프로세스를 끼워 넣는" 것에 가깝습니다.

이 Pod를 지우면 무슨 일이?

bare Pod의 한계를 직접 확인합니다 — 여기가 이번 실습의 핵심 교훈입니다.

$ kubectl delete pod nginx-test
$ kubectl get pods
무슨 일이 일어나나 아무 일도 일어나지 않습니다 — 그게 포인트입니다. 이 Pod는 kubectl run으로 직접 만든 "주인 없는(bare)" Pod라서, 이걸 계속 유지시켜야 한다고 감시하는 컨트롤러가 없습니다. 지우면 그냥 사라지고 끝입니다. 실무에서 Pod를 직접 만들지 않고 항상 Deployment를 쓰는 이유가 바로 이겁니다.
확인 get pods 결과가 텅 비어 있어야 합니다.
8

이번엔 Deployment로 선언하기

"명령"이 아니라 "원하는 상태"를 선언하는 방식(declarative)으로 전환합니다.

# nginx-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx-practice
  template:
    metadata:
      labels:
        app: nginx-practice
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          ports:
            - containerPort: 80

$ kubectl apply -f nginx-deployment.yaml
무슨 일이 일어나나 run과 달리 apply는 "지금 당장 이걸 해라"가 아니라 "클러스터가 항상 이 상태를 유지하도록 해라"는 선언입니다. API 서버가 이 요청을 받으면:
  1. Deployment 컨트롤러가 이 Deployment를 보고 ReplicaSet을 하나 생성
  2. ReplicaSet 컨트롤러가 replicas: 2를 보고 라벨(app: nginx-practice)이 일치하는 Pod가 2개가 될 때까지 계속 만듦
  3. 각 Pod는 자신을 만든 ReplicaSet을, 그 ReplicaSet은 Deployment를 ownerReferences로 기억합니다 — 이 소유 관계가 다음 단계에서 중요해집니다
9

소유 관계 눈으로 확인

Deployment → ReplicaSet → Pod 체인을 한 화면에서 봅니다.

$ kubectl get deploy,rs,pods -l app=nginx-practice
무슨 일이 일어나나 세 종류의 오브젝트가 동시에 조회됩니다. ReplicaSet 이름은 nginx-deployment-<해시>, Pod 이름은 그 뒤에 랜덤 문자열이 또 붙는 식으로 이름 자체가 소유 관계를 드러냅니다. Deployment를 이미지 버전업 등으로 업데이트하면, 기존 ReplicaSet은 0개로 줄이고 새 해시의 ReplicaSet을 새로 만드는 방식으로 롤링 업데이트가 이뤄집니다 (지금 단계에서는 눈으로만 확인).
10

자가치유(self-healing) 라이브로 보기

이번 실습에서 가장 극적인 순간 — Pod를 죽여도 바로 살아납니다.

# 터미널 A: 계속 지켜보기
$ kubectl get pods -l app=nginx-practice -w

# 터미널 B: 하나 강제로 삭제
$ kubectl delete pod <위에서-확인한-pod-이름>
무슨 일이 일어나나 터미널 A 화면에서 실시간으로: 지운 Pod가 Terminating으로 바뀌는 순간, ReplicaSet 컨트롤러가 "실제 개수(1) ≠ 원하는 개수(2)"를 감지하고 1초 내로 새 Pod를 만드는 게 그대로 보입니다. 6단계의 bare Pod와 정확히 같은 동작(삭제)인데 결과가 완전히 다른 이유 — 이번엔 지켜보는 컨트롤러가 있다는 것뿐입니다.
11

스케일 조정

스케일링이 자가치유와 같은 메커니즘이라는 걸 확인합니다.

$ kubectl scale deployment nginx-deployment --replicas=4
$ kubectl get pods -l app=nginx-practice
무슨 일이 일어나나 이 명령은 Deployment 오브젝트의 spec.replicas 필드 값을 2에서 4로 바꿀 뿐입니다. 그 다음은 9단계와 완전히 똑같은 조정 루프가 처리합니다 — "실제(2) ≠ 원하는(4)"를 감지하고 Pod 2개를 추가로 만듭니다. 자가치유와 스케일링이 사실은 하나의 메커니즘이라는 게 이번 실습의 결론입니다.
12

정리

클러스터를 깨끗한 상태로 되돌립니다.

$ kubectl delete deployment nginx-deployment
$ kubectl get all -l app=nginx-practice
무슨 일이 일어나나 Deployment 하나만 지웠는데 ReplicaSet과 Pod까지 전부 사라집니다. API 서버의 가비지 컬렉터가 ownerReferences 체인을 따라가며 부모가 사라진 자식 오브젝트를 연쇄적으로 정리하기 때문입니다 (Deployment → ReplicaSet → Pod 순서로 삭제).
확인 마지막 명령 결과가 비어있으면 01단계 실습 완료입니다.
막히는 지점(이미지 pull 실패, Pending에서 안 넘어감, exec 안 됨 등)이 생기면 그 시점의 kubectl describe pod <이름> 출력을 그대로 들고 오세요 — Events 섹션만 보면 대부분 원인이 바로 보입니다.
